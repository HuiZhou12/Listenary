## 2. 识别规则（写入实施，不得偏离）

**识别必须结合三类证据，不得仅凭字符串长度或字符集推断：**

| 证据 | 作用 | 说明 |
|---|---|---|
| **A. Header 名称规则** | 主判据 | 名单需覆盖 `cookie / set-cookie / authorization / proxy-authorization / x-api-key / api-key / apikey / appkey / app_key / appsecret / app_secret / x-token / token / access-token / refresh-token / id-token / session / sessionid / jwt / sign / signature / x-signature / x-sign / qskey / pskey / qm_keyst / credential / password / passwd` 等（可扩展；大小写不敏感、连字符与下划线归一） |
| **B. 明确的敏感标记** | 权威判据 | 配置中显式声明的"该 header 为敏感"（本次 F0 新增的模型字段）；一旦标记，**无条件**按敏感处理 |
| **C. 用户确认** | 兜底判据 | 名称未命中、但用户认为敏感时，必须能显式标记并迁移 |

**禁止**：把"长度 ≥16 / 字符集受限"当作**自动迁移**依据。值形态启发式**只能**用于生成"**待用户确认**"的候选清单。

**判定与处置（三态闭合，每一条 header 都必须落到其中一态）**：

| 状态 | 条件 | 处置 |
|---|---|---|
| `sensitive` | A 命中 **或** B 标记 | 进入迁移流程 |
| `needs-user` | 名称未命中、但值形态可疑（启发式） | **不迁移**；保留原配置不动；界面列出该 header（**只列名称**）并请用户选择"标记为敏感 / 确认为非敏感" |
| `plain` | 名称未命中且用户确认非敏感 | 保留明文（无害）；不得因迁移被删除或改写 |

**不得静默丢弃**：任何 header 都必须有明确结果（迁移 / 保留 / 待确认），且结果写入迁移报告（只写名称与状态，**不写值**）。

## 3. 凭据槽位命名与共享规则

- 默认槽位名：**`<providerId>/<capability>/<normalizedHeaderName>`**
  - `normalizedHeaderName` = 小写、去空白、非字母数字字符归一为 `-`。
  - 目的：**同名 header 在不同能力使用不同凭据时不得相互覆盖**（用户明确要求）。
- **共享秘密**：只有通过**显式凭据引用**（让多个能力指向同一 `credentialReference`）才能共享；
  **不得**因为两个 header 的值相同就自动合并（用户明确要求）。
- 值完全相同的判断一律**不作为合并依据**。
- 槽位名一经写入即**稳定**（迁移可重放、可幂等）：重复执行迁移不得新建重复槽位、不得改名。

## 4. 迁移流程（成功 / 失败 / 恢复）

**粒度：每个 `(provider, capability, header)` 独立判断；但以 entry 为原子单位收敛。**

1. **只识别**：产出识别报告（§2 三态 + 每个敏感项的槽位名）。**此步不写任何东西。**
2. **用户确认**：报告中的 `needs-user` 项必须由用户裁定（标记敏感 / 确认非敏感）；`sensitive` 项需用户放行后才执行真实迁移。
3. **按 entry 事务化执行**：
   - 逐项写入 OS 凭据管理器（`OnlineMusicCredentialAccess.save(reference, value)`）；
   - **立即回读校验**（`readCredential(reference)` 与原值逐字节一致）；
   - 全部项成功 ⇒ 才改写该 entry 的配置（header 改为引用形式；移除明文）；
   - 改写后**重新解析校验**（新配置能被 `OnlineMusicSettings.fromJson` 正常读回）。
4. **失败处理**：任一步失败 ⇒ **整条 entry 回滚**（不写入槽位 / 已写入的槽位删除 / 配置不改）⇒ **绝不留下半迁移**。
   回滚失败 ⇒ **停止整个迁移并报告**，不得继续处理其它 entry 以掩盖问题（用户明确要求）。
5. **成功后的清理**：确认"凭据可读 + 新配置可解析 + **旧配置中明文已移除**"三者同时成立后，才算该 entry 完成。
6. **幂等**：重复执行迁移必须安全（已迁移项跳过；`plain` 项不动；`needs-user` 项仍待用户）。

**顺序约束**：先写凭据 → 再改配置；**永不**"先删明文再写凭据"。

## 5. 明文禁止面（全部必须遵守）

- 明文中**不得**出现在：普通日志、诊断报告、审计报告、Git、**非安全备份**、**任何额外文件**（含临时文件）。
- 内存中的明文只在迁移/注入的必要范围内存在；不得进入 `toString()`、异常消息、崩溃上报。
- 既有明文配置**只在迁移成功后**移除；迁移失败必须原样保留（可恢复）。
- 界面显示：敏感头一律**遮蔽**（不得在表单里明文回显）；`needs-user` 项**只列名称**。

## 7. Base URL 校验

1. **非法 baseUrl 必须得到明确的校验错误**，**不得**静默替换为 `api.chksz.com` 或任何其它主机。
2. **必须区分两种来源**（不得为了修非法 URL 而破坏合法旧配置）：
   - **缺失**（旧配置未提供该值）⇒ 允许使用既有默认值（`defaultOnlineMusicBaseUrl`），**行为与旧版一致**；
   - **用户显式提供的非法值** ⇒ **校验失败并报错**，不替换、不发请求、提示用户修正。
3. 校验时机：**保存时**（拒绝保存）与**发请求前**（防御性再校验）。
4. **验证方式（不得用真实 Key 打错误地址）**：模拟传输层 + 测试服务 + **假凭据**，断言：
   - 非法地址**不触发任何请求**（传输层调用次数为 0）；
   - 请求目标**不被替换**（无 `api.chksz.com` 目标出现）；
   - **不向非预期主机发送任何敏感信息**（假凭据不出现在任何请求中）；
   - **合法的旧配置仍然兼容**（缺省值仍走默认、显式合法值仍生效）。

### 10.4 合成测试必须覆盖的场景（对应 §10.1 第 4 条）

1. 迁移**成功**（写槽位 → 回读一致 → 配置改写 → 重新解析 → 明文已移除）；
2. **凭据写入失败**（`save` 抛错 ⇒ 整条 entry 不迁移、配置不变）；
3. **回读不一致**（写入成功但 `readCredential` 与原文不符 ⇒ 回滚槽位、配置不变）；
4. **配置保存失败**（槽位已写但配置写盘失败 ⇒ 回滚槽位）；
5. **回滚失败**（槽位删除失败 ⇒ **停止整个迁移并报告**，不得继续处理其它 entry）；
6. **幂等重放**（重复执行不新建重复槽位、不改名、`plain` 项不动）；
7. **旧配置中不应再保留明文敏感值**（迁移成功后对配置全文断言：不再出现该值）。

## 11. 决策 A / B 与存储冲突约束（2026-10-09 追加，已裁定）

### 11.1 A. `needs-user` 裁定入口（同意）

- **位置**：能力编辑器**请求头行内**增加「敏感」勾选框 + 一句简短说明；**不新增独立页面**（避免 F0 扩到设置页重构）。
- **模型**：`OnlineMusicHeaderSpec` 新增**可选** `sensitive` 字段，**缺省 `false`**；`toJson` 在 `false` 时**省略**该键；`fromJson` 容缺；**旧配置往返后逐字节语义不变**。
- **规则（必须实现）**：
  1. **明确标记为敏感**的 Header ⇒ **必须**走安全凭据存储 + 引用流程；
  2. **仅由值形态产生的歧义项** ⇒ **必须由用户裁定**，**不得自动迁移**；
  3. 标记敏感后，若**安全存储或配置保存失败** ⇒ **不得静默回退为明文保存或明文发送**，**也不得显示成功** ⇒ 一律**明确报错**。

### 11.2 B. portable 模式：跳过迁移，但必须安全失败（同意）

1. portable 模式下**无法持久化安全凭据** ⇒ **跳过迁移**、**原配置保持不变**，并**明确提示用户切到安装版完成迁移**；
2. **不得**把敏感值写入内存凭据后再删除原值（那等于重启即丢）；
3. 对**已明确标记为敏感、但没有可用安全凭据引用**的明文 Header：**发请求时必须返回明确错误**，**不得静默降级为明文发送**；
4. **不得**把"跳过迁移"报告为成功；**不得**声称现有明文"已经安全"。

### 11.3 存储冲突约束（针对 `CredWrite` 的"存在即覆盖"语义）

写入目标槽位**之前必须检查冲突**：

| 目标槽位状态 | 处置 |
|---|---|
| 不存在 | 允许**新建** |
| 已存在且**内容完全相同** | 视为**幂等重放**（通过，不重复写） |
| 已存在但**内容不同**，或**无法可靠确认** | **停止并报告**，**不得覆盖**原凭据 |
| 不同槽位之间 | **不得**因明文值相同而自动合并 |
| **Header 名归一化后发生碰撞**（如 `X-Token` 与 `x_token` 归一后同名） | **必须失败并报告** |

> **边界说明（重要）**：上述"不得覆盖"约束**只适用于迁移路径**。
> 用户在凭据界面**主动更新**某个引用的值是**合法轮换**，**必须允许覆盖**（否则无法更换 Key）。

### 11.4 影响面

| 维度 | 影响 |
|---|---|
| **配置兼容性** | 仅**新增可选** `sensitive` 字段（缺省 false、false 时不写盘）⇒ 旧配置读取与写回**语义不变**；**不需要迁移 `sensitive` 本身**。但**一旦用户勾选敏感**，该 Header 进入"必须有引用"状态 ⇒ 该能力的请求在凭据就位前**会明确失败**（见下"运行时行为"） |
| **运行时行为** | ① `sensitive:true` + 明文 `value`（未迁移）⇒ **明确错误、不发请求**（传输层调用次数必须为 0）；② `sensitive:true` + 有效引用 ⇒ 正常注入；③ `sensitive:false` ⇒ 行为与今天完全一致 |
| **便携模式行为** | 跳过迁移、配置逐字节不变、提示切换安装版；**不写内存槽位**、**不报成功**、**不声称明文安全**；"portable 下的安全存储"登记为**独立后续项**（不塞进 F0） |
| **验收测试** | 在 §10.4 的 7 项之外**新增 7 项**（见 §11.5） |

### 11.5 新增验收测试（合入 §10.4 形成 14 项）

1. `sensitive:true` + 明文 `value`（未迁移）⇒ **发请求返回明确错误**，且**传输层调用次数 = 0**；
2. **保存** `sensitive:true` + 明文 `value` ⇒ **被拒**并提示先填写凭据（**我补充的决定**：不应让用户存下一份"跑不起来"的配置；若你不同意可改为允许保存但运行时报错）；
3. 目标槽位**已存在且内容不同** ⇒ **停止、不覆盖、报告**；
4. 目标槽位**已存在且内容相同** ⇒ **幂等通过**、不重复写；
5. **Header 名归一化碰撞** ⇒ **失败并报告**；
6. **portable 模式** ⇒ 跳过迁移、**配置逐字节不变**、出现提示、**未写入内存槽位**、**未报成功**；
7. **用户主动更新凭据** ⇒ **允许覆盖**（与迁移路径明确区分，防止规范化后无法轮换 Key）。
